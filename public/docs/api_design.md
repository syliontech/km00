# API Design and Conventions

This document outlines the conceptual design for API endpoints related to core entities and specific logic for item number generation.

## General Conventions

*   **Base URL:** All API endpoints are relative to a base URL (e.g., `/api/v1`).
*   **Authentication:** Assumed to be handled (e.g., JWT tokens in Authorization header).
*   **Error Handling:** Standard HTTP status codes will be used. Error responses will typically include a JSON body with `{"error": "message"}`.
*   **Timestamps:** `CreatedAt` and `UpdatedAt` fields are automatically managed by the database.

## 1. Categories API (`/categories`)

Manages product categories.

### `POST /categories`

*   **Description:** Creates a new category.
*   **Request Body:**
    ```json
    {
      "CategoryName": "Electronics",
      "CategoryCode": "ELEC",
      "ParentCategoryID": null, // or ID of parent category
      "Description": "All kinds of electronic devices and components."
    }
    ```
*   **Responses:**
    *   `201 Created`: Successfully created. Response body includes the newly created category object.
        ```json
        {
          "CategoryID": 1,
          "CategoryName": "Electronics",
          "CategoryCode": "ELEC",
          "ParentCategoryID": null,
          "Description": "All kinds of electronic devices and components.",
          "CreatedAt": "2023-10-27T10:00:00Z",
          "UpdatedAt": "2023-10-27T10:00:00Z"
        }
        ```
    *   `400 Bad Request`: Invalid input (e.g., missing required fields, invalid `CategoryCode` format or `ParentCategoryID` not existing).
    *   `409 Conflict`: `CategoryCode` already exists.

### `GET /categories`

*   **Description:** Lists all categories.
*   **Query Parameters:**
    *   `page` (integer, optional, default: 1): For pagination.
    *   `limit` (integer, optional, default: 20): Number of items per page.
    *   `parent_id` (integer, optional): Filter by `ParentCategoryID`.
*   **Responses:**
    *   `200 OK`: Response body is an array of category objects.
        ```json
        [
          {
            "CategoryID": 1,
            "CategoryName": "Electronics",
            "CategoryCode": "ELEC",
            // ... other fields
          },
          {
            "CategoryID": 2,
            "CategoryName": "Books",
            "CategoryCode": "BOOK",
            // ... other fields
          }
        ]
        ```

### `GET /categories/{category_id}`

*   **Description:** Gets a specific category by its ID.
*   **Path Parameters:**
    *   `category_id` (integer, required): The ID of the category to retrieve.
*   **Responses:**
    *   `200 OK`: Response body includes the category object.
    *   `404 Not Found`: Category with the given ID does not exist.

### `PUT /categories/{category_id}`

*   **Description:** Updates an existing category. Only provided fields in the request body will be updated.
*   **Path Parameters:**
    *   `category_id` (integer, required): The ID of the category to update.
*   **Request Body:**
    ```json
    {
      "CategoryName": "Consumer Electronics",
      "Description": "Updated description for consumer electronics."
      // Other fields like ParentCategoryID or CategoryCode can also be updated
    }
    ```
*   **Responses:**
    *   `200 OK`: Successfully updated. Response body includes the updated category object.
    *   `400 Bad Request`: Invalid input.
    *   `404 Not Found`: Category with the given ID does not exist.
    *   `409 Conflict`: If trying to update `CategoryCode` to one that already exists.

### `DELETE /categories/{category_id}`

*   **Description:** Deletes a category.
*   **Path Parameters:**
    *   `category_id` (integer, required): The ID of the category to delete.
*   **Responses:**
    *   `204 No Content`: Successfully deleted.
    *   `404 Not Found`: Category with the given ID does not exist.
    *   `409 Conflict`: Deletion restricted by foreign key constraints (e.g., if `ProductFamilies` or child `Categories` reference it and `ON DELETE` is `RESTRICT` or `SET NULL` is not applicable/desired for all children). The `ON DELETE SET NULL` for `ParentCategoryID` means child categories won't prevent deletion but will become top-level. However, `ProductFamilies` have `ON DELETE RESTRICT`.

## 3. Item Number Generation Logic (`ProductFamilyID`)

This section details the conceptual logic for generating `ProductFamilyID` when a new product family is created via `POST /productfamilies`.

1.  **Receive Request:** The service layer receives the `POST /productfamilies` request, which includes `CategoryID`, `FamilyName`, and `Description`.
2.  **Fetch Category Code:**
    *   The service queries the `Categories` table using the provided `CategoryID` to retrieve its `CategoryCode`.
    *   If the `CategoryID` is invalid or the category is not found, an appropriate error (e.g., 400 Bad Request) is returned.
3.  **Determine Next Sequential Number:**
    *   The service queries the `ProductFamilies` table.
    *   It filters records where `ProductFamilyID` starts with the retrieved `CategoryCode` (e.g., `LIKE 'ELEC-%'`).
    *   From these records, it extracts the numeric part of the `ProductFamilyID` (e.g., from "ELEC-0001", extract "0001"; from "ELEC-0012", extract "0012").
    *   It finds the highest sequential number among these. If no existing product families exist for that category code, the sequence starts at 0.
4.  **Increment and Pad:**
    *   The highest sequential number is incremented by 1.
    *   The new number is padded with leading zeros to a fixed length (e.g., 4 digits, so 1 becomes "0001", 12 becomes "0012", 123 becomes "0123").
5.  **Form New `ProductFamilyID`:**
    *   The new `ProductFamilyID` is constructed by concatenating: `CategoryCode` + "-" + `padded_sequential_number`.
    *   Example: If `CategoryCode` is "HTOOL" and the next number is 42, the `ProductFamilyID` becomes "HTOOL-0042".
6.  **Save New Product Family:**
    *   The new `ProductFamily` entity is created with this generated `ProductFamilyID` and the other details from the request.
    *   The entity is saved to the database.
    *   This operation should ideally be atomic or handled within a transaction to prevent race conditions if multiple requests for the same category arrive concurrently (e.g., using database-level sequences or locking if necessary for high-concurrency scenarios, though a simpler approach is described here).

This conceptual logic ensures that `ProductFamilyID` values are unique, human-readable, and follow a consistent pattern based on their category.

## 4. Product Variants API (`/productvariants`)

Manages specific product variants, which are instantiable versions of a product family.

### `POST /productvariants`

*   **Description:** Creates a new product variant. `VariantSKU` can be auto-generated or optionally provided.
*   **Request Body:**
    ```json
    {
      "ProductFamilyID": "ELEC-0001",
      "VariantName": "Smartphone X, 128GB, Black",
      "VariantSKU": "OPTIONAL-SKU-123", // If not provided, system generates one
      "Description": "The latest Smartphone X with 128GB storage in black.",
      "ImageURL": "https://example.com/image.jpg",
      "Status": "Active",
      "Specifications": [ // Array of specifications for this variant
        { "AttributeID": 101, "AttributeValue": "Black" }, // e.g., AttributeID for "Color"
        { "AttributeID": 102, "AttributeValue": "128GB" }  // e.g., AttributeID for "Storage"
      ]
    }
    ```
*   **Key Backend Logic:**
    *   Validate `ProductFamilyID`.
    *   If `VariantSKU` is not provided, generate it (see section 5).
    *   Validate `VariantSKU` uniqueness if provided.
    *   Create `ProductVariants` record.
    *   For each item in `Specifications`:
        *   Validate `AttributeID` (must exist and belong to the `ProductFamilyID`).
        *   Create `ProductVariantSpecifications` record linking the variant to the attribute and value.
    *   All creations should be part of a single transaction.
*   **Responses:**
    *   `201 Created`: Successfully created. Response body includes the new product variant object with its specifications.
        ```json
        {
          "VariantID": 1,
          "ProductFamilyID": "ELEC-0001",
          "VariantSKU": "VAR-0000001", // or the one provided
          "VariantName": "Smartphone X, 128GB, Black",
          "Description": "The latest Smartphone X with 128GB storage in black.",
          "ImageURL": "https://example.com/image.jpg",
          "Status": "Active",
          "CreatedAt": "2023-10-27T11:00:00Z",
          "UpdatedAt": "2023-10-27T11:00:00Z",
          "Specifications": [
            { "SpecificationID": 1, "AttributeID": 101, "AttributeName": "Color", "AttributeValue": "Black" },
            { "SpecificationID": 2, "AttributeID": 102, "AttributeName": "Storage", "AttributeValue": "128GB" }
          ]
        }
        ```
    *   `400 Bad Request`: Invalid input (e.g., missing fields, invalid `ProductFamilyID`, invalid `AttributeID`).
    *   `409 Conflict`: `VariantSKU` already exists.

### `GET /productvariants`

*   **Description:** Lists all product variants.
*   **Query Parameters:**
    *   `page` (integer, optional, default: 1).
    *   `limit` (integer, optional, default: 20).
    *   `product_family_id` (string, optional): Filter by `ProductFamilyID`.
    *   `status` (string, optional): Filter by `Status`.
    *   `sku` (string, optional): Search by `VariantSKU`.
*   **Responses:**
    *   `200 OK`: Array of product variant objects. Each object can optionally include its specifications.

### `GET /productvariants/{variant_id_or_sku}`

*   **Description:** Gets a specific product variant by its internal `VariantID` or unique `VariantSKU`.
*   **Path Parameters:**
    *   `variant_id_or_sku` (integer or string, required).
*   **Responses:**
    *   `200 OK`: Product variant object, including its specifications.
    *   `404 Not Found`.

### `PUT /productvariants/{variant_id_or_sku}`

*   **Description:** Updates a product variant. `VariantSKU` typically cannot be changed once set. Specifications are updated by providing the full desired list of specifications.
*   **Request Body:** Fields to update. To update specifications, provide the new list.
    ```json
    {
      "VariantName": "Smartphone X, 128GB, Midnight Black",
      "Status": "Discontinued",
      "Specifications": [
        { "AttributeID": 101, "AttributeValue": "Midnight Black" },
        // Note: If a previous spec is omitted, it might be removed or marked inactive.
        // Alternatively, provide specific endpoints for managing specifications if partial updates are common.
        { "AttributeID": 103, "AttributeValue": "Snapdragon 8 Gen 2" } // Adding a new spec
      ]
    }
    ```
*   **Key Backend Logic:**
    *   Update `ProductVariants` record.
    *   For `Specifications`:
        *   The simplest approach is to delete all existing `ProductVariantSpecifications` for the variant and insert the new ones. This must be done in a transaction.
        *   Alternatively, implement a diffing mechanism to add/update/delete individual specifications.
*   **Responses:**
    *   `200 OK`: Updated product variant object.
    *   `400 Bad Request`.
    *   `404 Not Found`.

### `DELETE /productvariants/{variant_id_or_sku}`

*   **Description:** Deletes a product variant. This will also delete associated `ProductVariantSpecifications` due to `ON DELETE CASCADE`.
*   **Responses:**
    *   `204 No Content`.
    *   `404 Not Found`.
    *   `409 Conflict`: If deletion is restricted by other tables (e.g., `CostEntries`, `BillOfMaterials`).

## 5. ProductVariantSKU Generation Logic

This section details the conceptual logic for generating `ProductVariantSKU` when a new product variant is created via `POST /productvariants` and `VariantSKU` is not provided in the request.

1.  **Trigger Condition:** `VariantSKU` is not provided in the request body.
2.  **Prefix:** A standard prefix is used, e.g., "VAR-".
3.  **Sequential Number:**
    *   The system needs to maintain a global counter for product variant SKUs. This could be:
        *   A dedicated sequence in the database (e.g., `product_variant_sku_seq`).
        *   Querying the `ProductVariants` table for the highest existing numeric part of SKUs that match the pattern "VAR-%", then incrementing. This is less robust for high concurrency.
    *   Using a database sequence is generally preferred for atomicity and performance.
4.  **Fetch Next Sequence Value:**
    *   Retrieve the next value from the sequence (e.g., `NEXTVAL('product_variant_sku_seq')`).
5.  **Pad Number:**
    *   The new number is padded with leading zeros to a fixed length (e.g., 7 digits, so 1 becomes "0000001", 123 becomes "0000123").
6.  **Form New `ProductVariantSKU`:**
    *   Concatenate: `Prefix` + `padded_sequential_number`.
    *   Example: If the prefix is "VAR-" and the next sequence value is 23, the `ProductVariantSKU` becomes "VAR-0000023".
7.  **Uniqueness Check (if not using DB sequence for generation):**
    *   Although the sequential generation aims for uniqueness, a final check against the `ProductVariants` table for the generated SKU is a good safeguard, especially if not using a database sequence directly for the number part. If a collision occurs (highly unlikely with sufficient padding and true sequences), retry with the next number.
8.  **Assign SKU:** The generated SKU is assigned to the new `ProductVariant` record before saving.

This ensures `ProductVariantSKU` values are unique and follow a consistent, predictable pattern.

## 6. Suggested Attributes API (`/suggestedattributes`)

Manages attributes that can be suggested for product families (e.g., "Color", "Size").

### `POST /suggestedattributes`

*   **Description:** Creates a new suggested attribute for a product family.
*   **Request Body:**
    ```json
    {
      "ProductFamilyID": "ELEC-0001",
      "AttributeName": "Screen Size",
      "AttributeType": "Number", // "Text", "Boolean", "Date"
      "IsRequired": false,
      "DefaultValue": "6.1",
      "Description": "Diagonal screen size in inches."
    }
    ```
*   **Key Backend Logic:**
    *   Validate `ProductFamilyID`.
    *   Ensure `AttributeName` is unique within the `ProductFamilyID`.
*   **Responses:**
    *   `201 Created`: Suggested attribute object.
    *   `400 Bad Request`.
    *   `409 Conflict`: Attribute name already exists for this product family.

### `GET /suggestedattributes`

*   **Description:** Lists suggested attributes.
*   **Query Parameters:**
    *   `product_family_id` (string, required): Filter by `ProductFamilyID`.
    *   `page`, `limit`.
*   **Responses:**
    *   `200 OK`: Array of suggested attribute objects.

### `GET /suggestedattributes/{attribute_id}`

*   **Description:** Gets a specific suggested attribute by its ID.
*   **Responses:**
    *   `200 OK`: Suggested attribute object.
    *   `404 Not Found`.

### `PUT /suggestedattributes/{attribute_id}`

*   **Description:** Updates a suggested attribute. `ProductFamilyID` likely cannot be changed.
*   **Request Body:** Fields to update.
    ```json
    {
      "AttributeName": "Display Size",
      "IsRequired": true
    }
    ```
*   **Responses:**
    *   `200 OK`: Updated suggested attribute object.
    *   `400 Bad Request`.
    *   `404 Not Found`.
    *   `409 Conflict`: If changing `AttributeName` to one that already exists for the family.

### `DELETE /suggestedattributes/{attribute_id}`

*   **Description:** Deletes a suggested attribute.
*   **Key Backend Logic:**
    *   Consider implications if `ProductVariantSpecifications` reference this attribute. The DDL has `ON DELETE RESTRICT`, so deletion will fail if it's in use. An alternative might be a "soft delete" or disassociation.
*   **Responses:**
    *   `204 No Content`.
    *   `404 Not Found`.
    *   `409 Conflict`: Attribute is in use by product variant specifications.

## 9. Cost Entries API (`/costentries`)

Manages cost information for product variants from different vendors.

### `POST /costentries`

*   **Description:** Creates a new cost entry for a product variant from a specific vendor.
*   **Request Body:**
    ```json
    {
      "VariantID": 1, // Internal ID of the product variant
      // Alternatively, could use "VariantSKU": "VAR-0000001" and resolve to VariantID in backend
      "VendorID": 1,
      "CostPrice": 99.50,
      "Currency": "USD",
      "ValidFrom": "2024-01-01",
      "ValidTo": "2024-12-31",
      "Notes": "Promotional price"
    }
    ```
*   **Key Backend Logic:**
    *   Validate `VariantID` (or resolve `VariantSKU`) and `VendorID`.
    *   Ensure uniqueness for `("VariantID", "VendorID", "ValidFrom")`.
*   **Responses:**
    *   `201 Created`: Cost entry object.
    *   `400 Bad Request`.
    *   `404 Not Found`: `VariantID` or `VendorID` not found.
    *   `409 Conflict`: Cost entry for this variant, vendor, and valid from date already exists.

### `GET /costentries`

*   **Description:** Lists cost entries.
*   **Query Parameters:**
    *   `variant_id` (integer, optional): Filter by internal `VariantID`.
    *   `variant_sku` (string, optional): Filter by `VariantSKU`.
    *   `vendor_id` (integer, optional): Filter by `VendorID`.
    *   `page`, `limit`.
*   **Responses:**
    *   `200 OK`: Array of cost entry objects.

### `GET /costentries/{cost_entry_id}`

*   **Description:** Gets a specific cost entry by its ID.
*   **Responses:**
    *   `200 OK`: Cost entry object.
    *   `404 Not Found`.

### `PUT /costentries/{cost_entry_id}`

*   **Request Body:** Fields to update.
    ```json

      "CostPrice": 95.00,
    ```

*   **Responses:**
    *   `200 OK`: Updated cost entry object.

    *   `404 Not Found`.

### `DELETE /costentries/{cost_entry_id}`

*   **Description:** Deletes a cost entry.
*   **Responses:**
    *   `204 No Content`.
    *   `404 Not Found`.

## 10. Bill of Materials (BOM) API (`/boms`)

Manages Bill of Materials, defining components for assembly/kit product variants.

### `POST /boms`

*   **Description:** Adds a component to the Bill of Materials for an assembly/kit product variant.
*   **Request Body:**
    ```json
    {
      "AssemblyVariantID": 1, // Internal ID of the "parent" assembly/kit variant
      // Alternatively: "AssemblyVariantSKU": "KIT-001"
      "ComponentVariantID": 5, // Internal ID of the "child" component variant
      // Alternatively: "ComponentVariantSKU": "COMP-A"
      "Quantity": 2,
      "UnitOfMeasure": "pcs",
      "Notes": "Screws for assembly"
    }
    ```
*   **Key Backend Logic:**
    *   Validate `AssemblyVariantID` and `ComponentVariantID` (or resolve SKUs).
    *   Ensure `AssemblyVariantID` is not the same as `ComponentVariantID`.
    *   Ensure uniqueness of `("AssemblyVariantID", "ComponentVariantID")`.
*   **Responses:**
    *   `201 Created`: BOM entry object.
    *   `400 Bad Request` (e.g., self-referencing BOM, component already exists in BOM for this assembly).
    *   `404 Not Found`: `AssemblyVariantID` or `ComponentVariantID` not found.

### `GET /boms` (Alternative: `GET /productvariants/{variant_id_or_sku}/bom`)

*   **Description:** Lists BOM entries for a specific assembly product variant.
*   **Query Parameters:**
    *   `assembly_variant_id` (integer, required if using `/boms`): The ID of the assembly variant.
    *   `assembly_variant_sku` (string, optional): Alternative to `assembly_variant_id`.
    *   `page`, `limit`.
*   **Path Parameter (if nested):**
    *   `variant_id_or_sku` (required): ID or SKU of the assembly variant.
*   **Responses:**
    *   `200 OK`: Array of BOM entry objects for the specified assembly. Each object would detail a component.
        ```json
        [
          {
            "BOMEntryID": 1,
            "AssemblyVariantID": 1,
            "ComponentVariantID": 5,
            "ComponentVariantSKU": "COMP-A", // Helpful to include
            "ComponentName": "Component A", // Helpful to include
            "Quantity": 2,
            "UnitOfMeasure": "pcs",
            "Notes": "Screws for assembly",
            "CreatedAt": "...",
            "UpdatedAt": "..."
          }
          // ... other components
        ]
        ```
    *   `404 Not Found`: Assembly variant not found.


### `GET /boms/{bom_entry_id}`

*   **Description:** Gets a specific BOM entry by its ID. This might be less common than getting the full BOM for an assembly.
*   **Responses:**
    *   `200 OK`: BOM entry object.
    *   `404 Not Found`.

### `PUT /boms/{bom_entry_id}`

*   **Description:** Updates a specific BOM entry (e.g., change quantity). `AssemblyVariantID` and `ComponentVariantID` should not be changed (delete and recreate if relationships must change).
*   **Request Body:**
    ```json
    {
      "Quantity": 3,
      "UnitOfMeasure": "pieces",
      "Notes": "Updated quantity"
    }
    ```
*   **Responses:**
    *   `200 OK`: Updated BOM entry object.
    *   `400 Bad Request`.
    *   `404 Not Found`.

### `DELETE /boms/{bom_entry_id}` (Alternative: `DELETE /productvariants/{variant_id_or_sku}/bom/{component_variant_id_or_sku}`)

*   **Description:** Removes a component from an assembly's BOM.
*   **Path Parameters (if nested):**
    *   `variant_id_or_sku`: ID/SKU of the assembly.
    *   `component_variant_id_or_sku`: ID/SKU of the component to remove.
*   **Responses:**
    *   `204 No Content`.
    *   `404 Not Found` (either BOM entry, assembly, or component not found).
