# Data Validation Strategy

This document outlines the data validation strategy for the API endpoints. Consistent and robust validation is crucial for data integrity and a good user experience.

## General Principles

1.  **Defense in Depth:** Validation should occur at multiple levels:
    *   **Client-Side (Optional but Recommended):** Basic checks in the UI (e.g., required fields, formats like email) can improve UX but should not be relied upon for security or data integrity.
    *   **API Gateway/Middleware (Early Checks):** Common checks like authentication, rate limiting, and basic request structure (e.g., valid JSON) can be done here.
    *   **Service Layer (Primary Validation):** This is where most business logic validation occurs. It ensures data is valid before interacting with the database.
    *   **Database Constraints:** The database schema (PK, FK, UNIQUE, NOT NULL, CHECK constraints) provides the ultimate guarantee of data integrity.

2.  **Fail Fast:** Validate as early as possible to provide quick feedback to the client and reduce unnecessary processing.

3.  **Clear Error Messages:** When validation fails, the API should return a `400 Bad Request` (or `422 Unprocessable Entity` if preferred for semantic distinction) status code. The response body should clearly indicate what went wrong, preferably with field-specific error messages.

    Example Error Response:
    ```json
    {
      "errors": [
        {
          "field": "CategoryName",
          "message": "CategoryName is required."
        },
        {
          "field": "CategoryCode",
          "message": "CategoryCode must be unique and was already taken."
        },
        {
          "field": "ParentCategoryID",
          "message": "ParentCategoryID '999' does not exist."
        }
      ]
    }
    ```

4.  **Centralized vs. Decentralized Validation Logic:**
    *   Common validation rules (e.g., string length, required, email format) can be handled by reusable utility functions or libraries.
    *   Entity-specific business rule validations are typically handled within the service layer corresponding to that entity.

## Validation Rules per Entity (POST/PUT Endpoints)

Below are key validation rules for each entity. This is not exhaustive but covers common scenarios. "DB" indicates the database also enforces this.

### 1. Categories (`/categories`)

*   **`CategoryName`**:
    *   Required.
    *   String.
    *   Max length: 255.
    *   Must be unique (DB also enforces via potential unique index if desired, beyond `CategoryCode`).
*   **`CategoryCode`**:
    *   Required.
    *   String.
    *   Max length: 10.
    *   Must be unique (DB: `UNIQUE`).
    *   Format: Alphanumeric, no spaces (e.g., `^[A-Z0-9]+$`).
*   **`ParentCategoryID`**:
    *   Optional (if NULL allowed).
    *   Integer.
    *   Must exist in `Categories.CategoryID` if provided (DB: Foreign Key).
    *   Should not be the `CategoryID` of the category itself (prevent self-referencing parent).
*   **`Description`**:
    *   Optional.
    *   String (text).

### 2. ProductFamilies (`/productfamilies`)

*   **`CategoryID`**:
    *   Required.
    *   Integer.
    *   Must exist in `Categories.CategoryID` (DB: Foreign Key `ON DELETE RESTRICT`).
*   **`FamilyName`**:
    *   Required.
    *   String.
    *   Max length: 255.
    *   Consider uniqueness within a Category or globally.
*   **`Description`**:
    *   Optional.
    *   String (text).
*   **`ProductFamilyID`** (Generated by backend, not part of request body for create, but validated if part of URL for PUT/DELETE):
    *   Format check (e.g., `CategoryCode-XXXX`).

### 3. ProductVariants (`/productvariants`)

*   **`ProductFamilyID`**:
    *   Required.
    *   String.
    *   Must exist in `ProductFamilies.ProductFamilyID` (DB: Foreign Key `ON DELETE RESTRICT`).
*   **`VariantName`**:
    *   Required.
    *   String.
    *   Max length: 255.
*   **`VariantSKU`**:
    *   Optional on create (generated if not provided).
    *   String.
    *   Max length: 100.
    *   Must be unique (DB: `UNIQUE`).
    *   Format: (e.g., `VAR-XXXXXXX` or other defined pattern).
*   **`Description`**:
    *   Optional.
    *   String (text).
*   **`ImageURL`**:
    *   Optional.
    *   String.
    *   Max length: 2048.
    *   Valid URL format.
*   **`Status`**:
    *   Optional (defaults to 'Draft').
    *   String.
    *   Value from a predefined list (e.g., 'Draft', 'Active', 'Discontinued').
*   **`Specifications` (array for POST, PUT may involve full replacement or partial updates):**
    *   Each object in the array:
        *   **`AttributeID`**: Required, Integer. Must exist in `SuggestedAttributes.AttributeID` AND be linked to the `ProductFamilyID` of the variant.
        *   **`AttributeValue`**: Required, String, Max length 255. Value should be consistent with `SuggestedAttributes.AttributeType` (e.g., if type is Number, value should be parseable as number).

### 4. SuggestedAttributes (`/suggestedattributes`)

*   **`ProductFamilyID`**:
    *   Required.
    *   String.
    *   Must exist in `ProductFamilies.ProductFamilyID` (DB: Foreign Key `ON DELETE CASCADE`).
*   **`AttributeName`**:
    *   Required.
    *   String.
    *   Max length: 255.
    *   Unique within the `ProductFamilyID` (DB: `UNIQUE` constraint on `("ProductFamilyID", "AttributeName")`).
*   **`AttributeType`**:
    *   Optional (defaults to 'Text').
    *   String.
    *   Value from a predefined list (e.g., "Text", "Number", "Boolean", "Date").
*   **`IsRequired`**:
    *   Optional (defaults to `FALSE`).
    *   Boolean.
*   **`DefaultValue`**:
    *   Optional.
    *   String. Max length 255.
*   **`Description`**:
    *   Optional.
    *   String (text).

### 5. Clients (`/clients`)

*   **`ClientName`**:
    *   Required.
    *   String. Max length: 255.
*   **`ContactName`**:
    *   Optional. String. Max length: 255.
*   **`ContactEmail`**:
    *   Optional. String. Max length: 255.
    *   Valid email format.
    *   Must be unique if provided (DB: `UNIQUE`).
*   **`ContactPhone`**:
    *   Optional. String. Max length: 50.
*   **`Address`, `City`, `State`, `Country`, `PostalCode`**: Optional strings with appropriate length limits.
*   **`ClientType`**:
    *   Optional. String. Max length: 50.
    *   Consider predefined list (e.g., "Individual", "Business").
*   **`Notes`**: Optional. String (text).

### 6. Vendors (`/vendors`)

*   **`VendorName`**:
    *   Required. String. Max length: 255.
*   **`ContactName`**:
    *   Optional. String. Max length: 255.
*   **`ContactEmail`**:
    *   Optional. String. Max length: 255.
    *   Valid email format.
    *   Must be unique if provided (DB: `UNIQUE`).
*   **`ContactPhone`**:
    *   Optional. String. Max length: 50.
*   **`Address`, `City`, `State`, `Country`, `PostalCode`**: Optional strings with appropriate length limits.
*   **`PreferredVendor`**:
    *   Optional (defaults to `FALSE`).
    *   Boolean.
*   **`VendorRating`**:
    *   Optional. Integer.
    *   Value between 1 and 5 (DB: `CHECK` constraint).
*   **`Notes`**: Optional. String (text).

### 7. CostEntries (`/costentries`)

*   **`VariantID`** (or `VariantSKU`):
    *   Required.
    *   Integer (if `VariantID`) or String (if `VariantSKU`).
    *   Must exist in `ProductVariants` (DB: Foreign Key `ON DELETE CASCADE`).
*   **`VendorID`**:
    *   Required. Integer.
    *   Must exist in `Vendors.VendorID` (DB: Foreign Key `ON DELETE RESTRICT`).
*   **`CostPrice`**:
    *   Required. Decimal.
    *   Must be non-negative (DB: `CHECK ("CostPrice" >= 0)`).
*   **`Currency`**:
    *   Optional (defaults to 'USD').
    *   String. Length 3 (e.g., ISO currency code).
*   **`ValidFrom`**:
    *   Optional (defaults to current date).
    *   Date. Valid date format.
*   **`ValidTo`**:
    *   Optional. Date. Valid date format.
    *   Must be after or equal to `ValidFrom` if both provided.
*   **Uniqueness**: `("VariantID", "VendorID", "ValidFrom")` must be unique (DB: `UNIQUE`).

### 8. BillOfMaterials (`/boms`)

*   **`AssemblyVariantID`** (or `AssemblyVariantSKU`):
    *   Required. Integer (or String for SKU).
    *   Must exist in `ProductVariants.VariantID` (DB: Foreign Key `ON DELETE CASCADE`).
*   **`ComponentVariantID`** (or `ComponentVariantSKU`):
    *   Required. Integer (or String for SKU).
    *   Must exist in `ProductVariants.VariantID` (DB: Foreign Key `ON DELETE RESTRICT`).
*   **`Quantity`**:
    *   Required. Integer.
    *   Must be greater than 0 (DB: `CHECK ("Quantity" > 0)`).
*   **`UnitOfMeasure`**:
    *   Optional. String. Max length 50.
*   **Self-Reference Check**: `AssemblyVariantID` must not be equal to `ComponentVariantID` (DB: `CHECK`).
*   **Uniqueness**: `("AssemblyVariantID", "ComponentVariantID")` must be unique (DB: `UNIQUE`).

## Implementation Notes

*   **Validation Libraries:** Utilize well-tested validation libraries for your programming language/framework (e.g., `express-validator` for Node.js/Express, `FluentValidation` for .NET, `Pydantic` for Python). These libraries simplify defining rules and collecting errors.
*   **Asynchronous Validation:** Some validation rules (e.g., checking if a foreign key exists) require database lookups. These should be handled asynchronously in the service layer.
*   **Contextual Validation:** Validation rules might change based on context (e.g., certain fields might become required if another field has a specific value). The service layer is best equipped to handle such complex logic.

By implementing a comprehensive validation strategy, the API will be more robust, secure, and easier for clients to integrate with.## Validation Rules per Entity (POST/PUT Endpoints)
